# 合并不是按下按钮：把 feat-20260725 安全送进 dev

今天我让 Mira 做了一件看起来很普通的事：把 `feat-20260725` 合并进 `dev`。

我只补了一条要求：

> 千万小心冲突。端口不一致的地方，以 `dev` 为准。

这句话很短，但真正进入工程现场以后，它至少包含三份合同：不能覆盖主线已经落地的工作，不能让功能分支悄悄改掉本地开发基线，也不能因为 GitHub 显示“可合并”，就把“没有文本冲突”误判成“没有风险”。

## 先写清楚冲突原则，再碰合并按钮

合并前最重要的动作，不是执行 `merge`，而是先明确谁对什么拥有最终解释权。

这次的原则很清楚：

```text
功能内容：来自 feat-20260725
主线现有工作：完整保留
端口与启动配置：以 dev 为准
```

当规则没有提前写清楚时，冲突处理就会退化成临场猜测。尤其是大量文件同时变化时，开发者很容易只盯着 Git 的冲突标记，却忽略那些能自动合并、语义上却已经改变了系统行为的配置。

所以第一步不是直接合并，而是确认两个分支的 HEAD、比较完整差异，并单独筛出端口、启动脚本和环境示例文件。

## PR 不是流程负担，而是检查面

这次没有直接把功能分支推入 `dev`，而是先创建了一个合并 PR。

PR 的价值不是多一道形式，而是把几个关键事实集中放到一个检查面上：

- base 是否真的是 `dev`；
- head 是否真的是 `feat-20260725`；
- GitHub 是否判断可自动合并；
- 功能分支究竟改了哪些文件；
- 最近主线上新增的生育报告、Vivliostyle 和 UChat artifact 工作是否被碰到；
- 端口差异是否只存在于预期文件。

这个 PR 一共包含 75 个提交、101 个变更文件。规模已经不适合靠“我大概看过了”来判断。

GitHub 给出的结果是 `mergeable: true`。这只能说明没有必须人工解决的文本冲突，不能说明配置语义完全正确。

## 真正的冲突没有红色标记

最后定位到的端口差异只有两个文件：

```text
runtime.config.cjs
.env.example
```

功能分支把默认端口改成了：

```text
backend  8788
desktop  5174
docs     4181
```

而 `dev` 当前使用的是：

```text
backend  8787
desktop  5173
docs     4180
```

Git 可以自动把这些内容合进去，所以不会出现传统意义上的冲突。但从工程合同看，这就是明确的语义冲突：功能分支无意间改变了所有开发者拉取主线后的默认启动行为。

这种冲突比红色标记更危险，因为它看起来像一次正常修改。

## 不做整文件 ours，而是做字段级合并

处理这两个文件时，不能简单地整文件选择 `dev`。

因为功能分支在 `.env.example` 里还增加了有价值的新内容：GitHub App 的可选配置说明。这部分应该保留。

最终处理是：

```text
保留 dev 的三个默认端口
+
保留 feat-20260725 新增的 GitHub App 配置
```

也就是说，不是“主线全赢”或“功能分支全赢”，而是按字段和职责合并。

我更愿意把这理解成一种配置审查：默认端口属于共享运行基线，GitHub App 说明属于新功能能力。它们虽然出现在同一个文件里，却不是同一类决策。

## 为什么先修功能分支，再执行合并

端口确认后，先在 `feat-20260725` 上把默认值改回 `dev` 的 8787、5173 和 4180，再执行合并。

这样做有两个好处。

第一，PR 的最终 diff 会直接表达正确结果。未来回看时，不需要依赖某个人记得“当时合并按钮里选了哪一边”。

第二，合并提交本身只负责汇合历史，不再夹带一组难以复核的临时冲突选择。

最终使用 merge commit 合入，保留了功能分支完整的提交历史。合并提交是：

```text
8cca6b3dcd745bbf4872634250dd239931ee6080
```

## 合并完成，不等于测试通过

合并后又重新读取了 `dev` 上的两个关键文件，确认最终默认端口仍然是：

```text
8787 / 5173 / 4180
```

同时，GitHub App 的新增说明也仍然存在。

但 GitHub 当时没有返回 CI 状态。因此这次能够确认的是：

- PR 已成功合并；
- 分支和提交关系正确；
- 端口结果正确；
- 目标配置内容正确。

不能确认的是“所有测试已经通过”。

工程现场里，最廉价也最危险的一句话就是“应该没问题”。没有测试结果时，就只报告已经验证的事实。

## 合并的可靠性来自证据链

这次没有复杂的冲突，也没有惊险的手工修复。真正重要的是，整个过程没有把“合并成功”压缩成一个按钮状态。

它保留了一条清楚的证据链：

```text
确认分支
→ 比较差异
→ 定位配置
→ 写明取舍
→ 修正功能分支
→ 合并
→ 回读主线结果
→ 如实报告验证边界
```

分支合并不是把两堆代码堆在一起。

它是在回答一个更具体的问题：哪些新东西应该进入主线，哪些主线事实不能被新功能顺手改写，以及我们凭什么相信最终结果真的是自己想要的那个结果。
