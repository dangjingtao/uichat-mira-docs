# 主线为什么要有最终解释权：从三个端口谈配置纪律

一次分支合并里，最显眼的通常是新页面、新接口和成片的业务代码。端口只是三行数字，很容易被当成无关紧要的小事。

但这次把 `feat-20260725` 合入 `dev` 时，我特意强调：

> 端口不一致之处，以 dev 为准。

不是因为 8787 比 8788 更正确，也不是因为主线天然高人一等。真正的原因是：默认配置代表当前团队共同生活的现实，改变它必须是一项被明确讨论的工程决策，而不能作为某个功能分支的副作用进入主线。

## 默认端口不是个人偏好

在本地开发环境里，默认端口会被很多地方依赖：

- 前端开发服务器；
- 后端 API；
- 代理配置；
- 文档站；
- 浏览器扩展；
- 本地脚本；
- 测试夹具；
- 开发者记忆中的启动地址。

因此下面这三行并不只是数字：

```text
backend  8787
desktop  5173
docs     4180
```

它们是一份共享运行合同。

一个功能分支当然可以为了本地并行启动临时使用 8788、5174 和 4181，但临时避让不应该自动升级为仓库新的默认现实。

## 环境覆盖和源码默认值是两层合同

Mira 的端口通过环境变量读取：

```text
UI_CHAT_BACKEND_PORT
UI_CHAT_DESKTOP_PORT
UI_CHAT_DOCS_SITE_PORT
```

这其实已经给了开发者足够的自由。

需要并行启动、避免冲突或做临时实验时，可以通过本地环境覆盖；没有显式配置时，仓库则回到主线约定的默认值。

这两层应该保持清楚：

```text
源码默认值 = 团队共享基线
环境变量   = 开发者本地选择
```

如果为了某次个人施工直接修改源码默认值，相当于把本地环境问题扩散给所有后来拉取代码的人。

一个成熟的配置系统，不是让所有人只能使用同一个端口，而是让“共享默认”和“个人覆盖”各自待在正确的位置。

## 功能分支应该带来能力，不应该顺手重写环境

`feat-20260725` 的主要任务是带入一批新功能。它在 `.env.example` 中新增了 GitHub App 的可选配置说明，这属于功能本身，应该保留。

同一个文件里，它也改变了三个默认端口。这部分不属于功能能力，而是开发现场留下的环境痕迹。

因此冲突处理不能简单理解成：

```text
这个文件选 dev
```

或者：

```text
这个文件选 feat
```

更合理的处理是：

```text
端口默认值      → dev
GitHub App 配置 → feat-20260725
```

工程合并的最小单位，经常不是文件，而是决策。

## “以 dev 为准”不是一句口头备注

一条规则只有落进代码和验证链，才算真正执行。

这次的做法是：

1. 先比较两个分支，定位所有端口差异；
2. 确认差异只出现在 `runtime.config.cjs` 和 `.env.example`；
3. 在功能分支上恢复 `dev` 的默认端口；
4. 保留功能分支新增的 GitHub App 说明；
5. 再执行 PR 合并；
6. 合并后重新读取 `dev` 上的最终文件。

最后确认主线仍然是：

```text
backend  8787
desktop  5173
docs     4180
```

这时“以 dev 为准”才不再是一句聊天记录，而是一个可以复核的仓库事实。

## 自动合并只能解决语法问题

GitHub 判断这次 PR 可以自动合并，没有文本冲突。

从 Git 的角度看，功能分支把 8787 改成 8788，是一条完全合法的修改。Git 不知道哪个端口代表团队当前约定，也不知道这个变化只是为了某次本地并行施工。

这提醒我，冲突至少有两种：

```text
文本冲突：两个分支改了同一段代码，Git 不知道怎么拼
语义冲突：Git 能拼起来，但拼出的行为不是我们想要的
```

自动化工具擅长发现前一种，后一种仍然需要明确的工程合同和定点检查。

## 对 Agent 来说，边界越清楚，执行越可靠

这次也让我重新确认了一件事：让 Agent 参与工程操作时，最重要的不是给它一句“谨慎一点”，而是给它可执行的优先级。

例如：

```text
端口不一致 → 保留 dev
主线新工作 → 不得覆盖
功能新增配置 → 应当保留
没有 CI 结果 → 不得声称测试通过
```

这些规则可以直接转化为搜索范围、文件检查、修改动作和最终报告边界。

含糊的要求只能得到含糊的谨慎；明确的合同才能得到可验证的执行。

## 主线负责表达当前共同现实

主线并不永远正确。默认端口以后也可能改变。

但改变应该发生在一项明确的任务里：说明为什么改、哪些依赖需要同步、如何迁移、如何验证。它不应该藏在一个大功能分支的 101 个文件里，被一次自动合并顺手带过去。

所以“以 dev 为准”的真正含义不是保守，而是责任：

> 在新的共识形成之前，主线继续表达团队当前共同使用、共同维护、共同承担后果的那套现实。

三行端口很小，但配置纪律往往就是从这些看起来不值得争论的小地方开始的。
